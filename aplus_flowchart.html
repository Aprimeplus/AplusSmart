🚀 เปิดโปรแกรมและ Login

ระบบเตรียมตัว, เชื่อมฐานข้อมูล, แล้วรอรับ User

🖥
⚙️ ระบบ
เปิดโปรแกรม A+ Smart
ระบบทำ 3 อย่างอัตโนมัติก่อนที่ใครจะ Login ได้:
  • 🔌 เชื่อมต่อฐานข้อมูล PostgreSQL (Server-APrime)
  • ⏰ ตั้งนาฬิกาเช็ค Notification ทุก 15 วินาที
  • 🔄 ตั้ง background task ทุก 1 ชั่วโมง (auto-submit งานค้าง)
🔐
⚙️ ระบบ
หน้า Login — ใส่ Username + Password
หลังกด Login ระบบจะดูว่า User คนนี้เป็น "ตำแหน่ง" อะไร แล้วเปิดหน้าจอที่ถูกต้องให้เลย:
  • 💼 Sales → หน้ากรอก SO
  • 👔 Sales Manager → หน้าคิว SO รออนุมัติ
  • 📦 Purchasing → หน้าสร้าง PO
  • 🏦 Pur Manager / Director → หน้าอนุมัติ PO
  • 🧮 HR → หน้าตรวจสอบและคิด Commission
1

💼 Sales กรอก SO แล้วส่งอนุมัติ

Sales Order = ใบบันทึกการขาย ยอด ลูกค้า และรายละเอียดทั้งหมด

1
💼 Sales
กรอกข้อมูล SO (Sales Order)
ใส่ข้อมูลทุกอย่างที่เกี่ยวกับการขายครั้งนี้:
  • 📄 เลข SO, ชื่อลูกค้า
  • 💰 ยอดขาย (Sales Amount), ค่า Service
  • 🧾 VAT, WHT ตามที่ลูกค้าตกลง
  • 🚚 วันส่งสินค้า, ที่อยู่จัดส่ง
  • 📅 กำหนดชำระเงิน
📝 สถานะ: Draft
2
💼 Sales
กด "Submit" ส่งให้ Sales Manager อนุมัติ
เมื่อกรอกครบแล้ว กด Submit — ระบบจะ:
  • 🔔 ส่ง Notification แจ้ง Sales Manager ทันที
  • 🔒 ล็อก SO ไม่ให้แก้ไขได้จนกว่าจะมีผล
⏳ สถานะ: Pending SM Approval
2

👔 Sales Manager ตรวจสอบและตัดสินใจ

จุดแรกที่ข้อมูลอาจ "โดนตีกลับ" — ถ้าข้อมูลไม่ถูกต้อง SO จะถูกส่งกลับ Sales

3
👔 Sales Manager
รับ Notification และตรวจสอบ SO
Sales Manager เห็น SO ในคิว จะดูข้อมูลทั้งหมด:
  • ยอดขายถูกต้องมั้ย
  • ชื่อลูกค้าและเงื่อนไขครบมั้ย
  • วันส่งสมเหตุสมผลมั้ย
4
👔 Sales Manager
ตัดสินใจ: อนุมัติ หรือ ปฏิเสธ?
มี 2 ทางเลือก:
✅ อนุมัติ (Approve)
SO ถูกส่งต่อให้ฝ่าย Purchasing เพื่อไปสร้าง PO ต่อ

🔔 ระบบแจ้ง Purchasing ทันที
✅ SM Approved
❌ ปฏิเสธ (Reject)
SM ต้องพิมพ์ "เหตุผล" ก่อนกด Reject

🔔 ระบบแจ้งกลับไปที่ Sales ทันที
❌ Rejected
🔴 เส้นทางเมื่อโดน Reject (ตีกลับ Phase 1)
↓
1. Sales Manager กด Reject + พิมพ์เหตุผล
2. ระบบเปลี่ยนสถานะ SO → "Edited" (ปลดล็อกให้แก้ไขได้)
3. 🔔 Notification ส่งไปหา Sales ทันที ว่า SO ถูกตีกลับ พร้อมเหตุผล
4. Sales เข้าไปแก้ไขข้อมูล ใน Tab "ประวัติการบันทึก"
5. Sales กด Submit ใหม่ → วนกลับไป Phase 2 ใหม่อีกรอบ

⚠️ วนได้ไม่จำกัดจนกว่า SM จะ Approve
3

📦 Purchasing สร้าง PO จาก SO ที่อนุมัติแล้ว

Purchase Order = ใบสั่งซื้อสินค้าจาก Supplier เพื่อมาตอบ SO ของลูกค้า

5
📦 Purchasing
รับงาน SO ที่ SM อนุมัติแล้ว
ในหน้า "รับงาน SO" จะเห็น SO ทั้งหมดที่ผ่าน SM มาแล้ว
เลือก SO ที่จะสร้าง PO → กดเปิดฟอร์ม
✅ SO Approved
6
📦 Purchasing
กรอกข้อมูล PO (Purchase Order)
  • 📄 เลข PO, ชื่อ Supplier (ผู้ขายส่ง)
  • 📋 รายการสินค้า + ราคาต้นทุน
  • 🔢 ราคาสินค้า (ระบบจะคำนวณต้นทุนแฝงตามนโยบายบริษัทอัตโนมัติ)
  • 🚢 ค่าขนส่ง (แยก: ไปโกดัง / ไปหน้างาน)
  • 🔧 ค่าบริการอื่นๆ (ตัด/เจาะ/ฯลฯ)
  • 🧾 VAT, WHT ตามที่ตกลง
📌 หมายเหตุการคำนวณต้นทุน: ระบบจะคำนวณต้นทุนแฝง (Overhead) เพิ่มเข้าไปในแต่ละรายการโดยอัตโนมัติ ตามมาตรฐานของบริษัท เพื่อให้ HR ใช้ตรวจสอบในขั้นตอนถัดไป
📝 สถานะ: Draft
7
📦 Purchasing
Submit PO เพื่อขออนุมัติ
กด Submit → ระบบสร้าง PDF เอกสาร PO และแจ้ง Manager 1 ทันที
⏳ สถานะ: Pending Approval
⏰ ระบบ Auto-Submit: ถ้า Purchasing สร้าง PO แล้วทิ้งไว้เป็น Draft เกิน 24 ชั่วโมง ระบบจะ Submit ให้เองอัตโนมัติ (background task ทำทุกชั่วโมง)
4

🏦 สายการอนุมัติ PO — หลายชั้น

จุดที่ 2 ที่ข้อมูลอาจ "โดนตีกลับ" — POอาจวิ่งไปมาหลายรอบก่อน Approve

8
🏦 Purchasing Manager 1
รับ Notification และตรวจ PO รอบแรก
Manager 1 ดู: ราคาต้นทุน, Supplier, รายการสินค้าถูกต้องมั้ย
✅ Manager 1 Approve
ส่งต่อให้ Manager 2 ต่อ
M1 Approved
❌ Manager 1 Reject
ตีกลับ Purchasing พร้อมเหตุผล
Rejected → ต้องแก้
9
🏦 Purchasing Manager 2 / Director
อนุมัติรอบสอง (ขึ้นอยู่กับมูลค่า PO)
PO มูลค่าสูงต้องผ่าน Director ด้วย — ตรวจในภาพรวมอีกรอบ
✅ Final Approve
PO ผ่านแล้ว ส่งต่อ HR ตรวจ
PO Approved
❌ Reject อีกครั้ง
ตีกลับ Purchasing อีกรอบ
Rejected
🔴 เส้นทางเมื่อ PO โดน Reject (ตีกลับ Phase 3)
↓
1. Manager กด Reject + พิมพ์เหตุผล
2. ระบบเปลี่ยนสถานะ PO → "Rejected"
3. 🔔 Notification ส่งกลับ Purchasing พร้อมเหตุผล
4. Purchasing เปิด PO ขึ้นมาแก้ไข ในหน้า "ประวัติ PO"
5. Purchasing กด Submit ใหม่ → วนกลับไป Phase 4 ใหม่
6. Manager ทุกคนต้องอนุมัติใหม่ทั้งหมด จากต้น

⚠️ วนได้ไม่จำกัดจนกว่าทุก Manager จะ Approve หมด
5

🧮 HR ตรวจสอบข้อมูลทั้งหมด

จุดที่ 3 ที่อาจตีกลับ — HR ตรวจตัวเลขทุกอย่างก่อนคำนวณ Commission

10
🧮 HR
ตรวจสอบข้อมูล SO vs ข้อมูล Express
HR จะ match ข้อมูลระหว่าง SO กับข้อมูลจากระบบ Express:
  • ตัวเลขตรงกันมั้ย
  • ตัวคูณต้นทุน (Cost Multiplier) ถูกต้องตามนโยบายหรือไม่
  • ค่า Service Fees บันทึกถูกหมวดมั้ย
  • ค่าขนส่งถูกต้องมั้ย
✅ ข้อมูลถูกต้อง
HR ผ่าน → คำนวณ Commission ได้เลย
HR Verified
⚠️ พบความผิดปกติ
HR Flag ปัญหา แจ้ง Purchasing แก้ไข
Flag Discrepancy
🔴 เส้นทางเมื่อ HR พบปัญหา (ตีกลับ Phase 3 หรือ 4)
↓
1. HR Flag ข้อผิดพลาดพร้อมรายละเอียด
2. 🔔 แจ้ง Purchasing หรือ Sales ว่าข้อมูลไม่ตรง
3. ฝ่ายที่รับผิดชอบแก้ไข (Purchasing แก้ PO หรือ Sales แก้ SO)
4. Submit ใหม่ → ผ่าน Approval Chain ใหม่ทั้งหมด
5. HR ตรวจอีกครั้ง จนกว่าข้อมูลจะถูกต้อง
5B

⏳ การเลื่อนรอบจ่าย Commission (Defer)

HR เห็นว่า SO ยังไม่พร้อมจ่ายคอมรอบนี้ → ขอเลื่อนไปรอบถัดไป → SM ตัดสินใจ

⏳
🧮 HR
HR กดปุ่ม "เลื่อนไปเดือนถัดไป (Defer)"
ระหว่างที่ HR กำลังตรวจสอบ SO อยู่ใน Phase 5 ถ้าเห็นว่า SO ยังไม่เหมาะสมจ่ายคอมรอบนี้ จะกดเลื่อนแทน:
  • 📋 เลือก ประเภทการเลื่อน (Defer Type)
  • 💬 ระบุเหตุผลที่ขอเลื่อน
  • 📅 ใส่วันส่งสินค้าใหม่ที่คาดว่าจะได้ (ถ้ามี)
  • 💳 ใส่วันชำระเงินใหม่ที่คาดว่าจะได้ (ถ้ามี)
  • ⚠️ ติ๊ก "Collection Risk สูง" (ถ้ามีความเสี่ยงเก็บเงินไม่ได้)
🟡 สิ่งที่ระบบทำทันทีเมื่อ HR กด Defer
↓
1. สถานะ SO เปลี่ยน → "Defer Requested"
2. ระบบบันทึกเดือนต้นทาง (defer_source_month/year) ไว้ว่าเดิมอยู่รอบไหน
3. commission_month/year เลื่อนไปเดือนถัดไปก่อน (รอ SM ยืนยัน)
4. 🔔 ระบบส่ง Notification ไปหา Sales ว่า SO ของตัวเองถูกขอเลื่อน
5. 🔔 ระบบส่ง Notification ไปหา Sales Manager ให้มาตัดสินใจ
⏳ Defer Requested
👁
💼 Sales (ฝ่ายขาย)
Sales เห็น Notification และดูสถานะ
Sales เปิดโปรแกรมมา → มี Popup บังคับรับทราบ ขึ้นมาทันที (DeferralNoticeDialog)

ใน Tab ติดตามสถานะ จะเห็น SO นี้แสดงว่า:
  • สถานะ: "รอ Manager อนุมัติเลื่อนจ่าย"
  • ปุ่มจะเป็น "รอผลตัดสินใจ" — กดไม่ได้ ต้องรอ SM
📌 Sales ทำอะไรไม่ได้ในขั้นตอนนี้ — ต้องรอให้ SM ตัดสินใจก่อน ถึงจะรู้ว่า SO นี้จะเลื่อนหรือบังคับจ่ายรอบนี้
⚖
👔 Sales Manager
SM เห็น Tab "⏳ คำขอเลื่อนรอบคอมฯ" และตัดสินใจ
SM เปิด Tab พิเศษที่แสดงรายการขอเลื่อนทั้งหมด จะเห็น:
  • เลข SO, ชื่อลูกค้า
  • 🔄 รอบที่ขอเลื่อนจาก → ไปเป็น (เช่น เมษายน → พฤษภาคม)
  • 👤 ชื่อ Sales + เหตุผลที่ HR ระบุ
✅ อนุมัติให้เลื่อน
SM กดปุ่ม "อนุมัติให้เลื่อน"
เลือกเดือน/ปีปลายทาง
ใส่เหตุผล
→ สถานะ: Deferred
❌ ไม่อนุมัติ (บังคับจ่าย)
SM กดปุ่ม "ไม่อนุมัติ (บังคับจ่าย)"
ใส่เหตุผล
SO กลับไปจ่ายรอบเดิม
→ สถานะ: Pending HR Approval
🟡 ผลลัพธ์ 2 ทาง หลัง SM ตัดสินใจ
↓
ทาง A — SM อนุมัติเลื่อน:
  • สถานะ → "Deferred"
  • commission_month/year ถูกเซ็ตเป็นเดือนปลายทางที่ SM เลือก
  • SO หายไปจากรอบนี้ → โผล่ในรอบเดือนหน้าแทน
  • 🔔 Sales รับ Notification พร้อม Popup บังคับรับทราบ
  • Sales เห็น SO นี้ในตาราง "รายการที่ถูกเลื่อน" พร้อมหมายเหตุ "เลื่อนมาจาก [เดือน]"
  • เดือนหน้า HR ต้องตรวจสอบ SO นี้ใหม่อีกครั้ง (Phase 5 อีกรอบ)

ทาง B — SM ไม่อนุมัติ (บังคับจ่าย):
  • สถานะ → "Pending HR Approval" (กลับมาจ่ายรอบเดิม)
  • 🔔 Sales รับ Notification พร้อม Popup บังคับรับทราบ
  • HR ต้องกลับมาตรวจสอบ SO นี้ใน Phase 5 ใหม่ → คำนวณ Commission รอบนี้ตามปกติ
📬
💼 Sales (ฝ่ายขาย)
Sales รับทราบผลการตัดสินใจ (Popup บังคับ)
เมื่อ Sales เปิดโปรแกรม ระบบจะ ดึง Notification [DEFER] ที่ยังไม่รับทราบ มาแสดง Popup บังคับทันที

Sales ต้องกด "รับทราบ" ก่อนถึงจะใช้งานระบบต่อได้
✅ กรณีเลื่อนสำเร็จ (Deferred): SO นี้จะโผล่อยู่ใน Tab "รายการที่ถูกเลื่อน" ในหน้า Sales จนกว่าเดือนนั้นจะถึงและ HR คำนวณเสร็จ

💰 HR คำนวณ Commission

🧮 HR
เลือก Commission Plan และคำนวณ

📊 กระบวนการประมวลผลอัตโนมัติ:

3. เทียบเคียงเป้ายอดขาย (KPI) และเงื่อนไขการทำงานของพนักงาน
4. คำนวณยอด Commission สุทธิเข้าสู่ระบบเงินเดือน
